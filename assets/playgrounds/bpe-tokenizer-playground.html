Tokenizer Lab

A language model never reads letters; it reads tokens. Byte-pair encoding (BPE) is the most common way to decide what the tokens are: start with one token per byte of your text, then repeatedly find the most frequent pair of neighbouring tokens and fuse it into a new token. Every fusion is a merge, and the list of merges is the tokenizer. Paste any text into Settings, press Play, and watch the vocabulary build and the token count fall. Then try the tokenizer you just trained on new text.

How it works

Everything on this page is computed in your browser from the text you give it. There is no pre-trained tokenizer; the merges you see are learned from that text only.

Training: the algorithm

  • Split into pre-tokens (optional, on by default). A word keeps its leading space, so “ low” and “low” at the start of a text are different pieces. Numbers, punctuation and runs of spaces become pieces of their own. Merges never cross from one piece to the next. The pattern is the GPT-2 style one: 's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+
  • Write every piece as UTF-8 bytes. The starting vocabulary is the 256 byte values (ids 0 to 255), so any text can be encoded and there is no “unknown” token. A letter such as “ä” is two bytes and starts as two tokens, which is why you see <C3>-style labels for half characters (try the German sample at 0 merges).
  • Count neighbouring pairs. For a pair of tokens (a, b), the count is
    count(a, b) = Σ over distinct pieces w of freq(w) × (number of places where a is directly followed by b inside w)
    Each distinct piece is counted once and weighted by how often it occurs, which gives the same result as scanning the whole text.
  • Merge the most frequent pair. It becomes a new token with id 256, 257, … in the order learned. In every piece the pair is replaced from left to right, without overlap. If two pairs tie, the pair with the smaller ids wins; this is a choice made on this page so that the result is deterministic.
  • Repeat until the budget “Max merges to learn” is used up, or the best pair occurs fewer times than the minimum you set, or every piece is a single token.

To tokenize new text, the learned merges are applied in the order they were learned: repeatedly take the earliest learned merge that applies to the piece and fuse every occurrence. This reproduces exactly what training did on the training text (checked below), and it is what the “Try the tokenizer on new text” box does.

What the plots mean

  • Count and saved. The count of the chosen pair never rises from one merge to the next. A merge can only create new pairs that involve the new token, and the new token occurs at most as often as the pair it came from; all other counts can only fall. I checked this on all samples in both modes. “Saved” is how many tokens the merge removed. It can be smaller than the count when occurrences overlap: on the text “aaaaaaa aaaa aaa” the first merge (a + a) has count 11 but removes 6 tokens.
  • Tokens against merges is the compression curve: how much shorter the text becomes. Bytes per token is its inverse view; one token per byte means 1.0.
  • Token lengths shows what the vocabulary is made of: single bytes at first, then longer pieces.

These samples are tiny, so read the numbers as an illustration. With minimum count 1 the English sample (610 bytes, 79 distinct words) ends after 232 merges at 119 tokens, which is one token per word: the tokenizer has memorised its own text. With minimum count 2 (the default) it learns 81 merges and ends at 270 tokens, 2.26 bytes per token. A real tokenizer is trained on far more text, where the merges describe common patterns of the language rather than the words of one paragraph.
  • A tokenizer fits the text it was trained on. I trained 80 merges on the English sample, and for comparison 80 merges on each target text, then tokenized that target text. German (522 bytes): 402 tokens (1.30 bytes per token) with the English merges against 246 (2.12) with merges learned from the German text. Python (253 bytes): 227 (1.11) against 88 (2.88). Numbers (218 bytes): 193 (1.13) against 91 (2.40). The second figure in each pair is measured on the text its merges were learned from, which flatters it, so the gap is overstated; the direction is what the demo shows. Petrov et al. (2023) study this effect at scale and report that the same text can need many more tokens in some languages than in others (up to about 15 times in their comparison).
  • Pre-tokenisation changes what a token can be. On the English sample with 100 merges, splitting into words first gives 251 tokens and none of the 100 merges contains a space or new line after its first byte. Treating the whole text as one piece gives 258 tokens, and 32 of the 100 merges contain a space or new line inside the token, so they span words. On the Python snippet, whole-text mode keeps going to 127 merges and ends with the entire snippet as a single token, while split-into-words stops after 64 merges at 88 tokens.

Checks I ran

  • An independent, deliberately naive Python implementation (it works on bytes objects, one entry per occurrence, with no frequency table) gives exactly the same merges, pair counts and token counts after every merge as the JavaScript on this page, for 23 combinations of text, pre-tokenisation mode and minimum count.
  • The Hugging Face tokenizers library (version 0.23.3, byte-level BPE with its GPT-2 pattern) gives the same number of tokens after 20 and after 60 merges on four of the samples (8 comparisons). I compared token counts only, not the merge order, because implementations may break ties differently and I did not check that.
  • Decoding the token ids returns the original text exactly, at several merge counts, in both modes. Tokenizing the training text with the first k merges gives exactly the token count recorded during training.

What this page leaves out

  • Real tokenizers add special tokens, sometimes normalise text before tokenizing, and use other pre-tokenisation patterns; none of that is modelled here.
  • Texts are limited to 50,000 characters (20,000 in whole-text mode, which is slower) so the page stays responsive.
  • Ties are broken by the smaller token ids; other implementations may choose differently and then produce a different, equally valid tokenizer.
